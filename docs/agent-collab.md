# Agent 协作总纲

> 本文档是 agent 在本仓库工作的**唯一**协作约定文件（入库、可移植：不含本机专属路径）。
> 本机的具体路径、命令与环境状态见仓库根 `AGENTS.md`（不入库）与 [当日 devnote 笔记](archive/refactor-2026/devnote/README.md)。
> 本文整合了原 agent-collab（通用约定）与 refactor-collab（重构约定），并收录原 R2 计划中的流程纪律（阶段门禁、行为档案机制）——改协作规则只改这里。

## 1. 硬规则（违反即返工）

- **git 唯一操作人是主 agent，子 agent 只读不写 git**；禁 `reset --hard` / `clean -f` / force push / rebase；先测试后提交；阶段 tag 兼作审查基准与回退锚点
- **push 时机由用户决定**，不主动 push；push 后确认 CI 双绿（ci.yml 架构守护+测试、release.yml testReleaseUnitTest）
- **并发会话可能同时在写仓**：动 git 前先全量核对 `git status`，出现异常改动停下问用户
- **重构中禁止向巨石文件追加新功能**，新功能一律新建文件
- **入库可移植性**：入库文件只含可移植内容，机器专属值外置到本机配置（详见 §4）

## 2. 入库可移植性

**入库文件尽量采用可移植的代码方案；迫不得已涉及本机路径时，明确单独告知用户。**

具体应用：

- 入库的配置（`gradle.properties`、`*.gradle.kts`、CI 工作流）**只含可移植内容** — 机器专属值一律外置到本机配置，并在入库文件中留注释说明约定
- 本机专属配置的三个去处（均不入库）：项目 `local.properties`、Gradle 主目录下的 `gradle.properties`、Gradle 主目录下的 `init.d/` 脚本
- 为什么严格：本仓库 CI（`.github/workflows/release.yml`）在 Linux 上构建，入库文件中的 Windows 路径会直接挂 CI；其他贡献者的机器同理
- 涉及本机路径的改动完成时，**单独**向用户报告涉及了哪些本机路径，与常规改动汇报分开

## 3. 构建验证循环

改动代码后按此循环验证，每步有明确完成标准：

1. **构建** — 执行项目约定的构建命令（本机命令见 `AGENTS.md`）→ 完成标准：`BUILD SUCCESSFUL`
2. **安装** — 安装到实机（`installDebug` 或 `adb install -r`）→ 完成标准：输出 `Success`；小米设备留意手机端弹窗确认
3. **启动验证** — 启动应用并确认前台 → 完成标准：`dumpsys activity activities` 中 `MainActivity` 位于 `topResumedActivity`
4. **日志** — `adb logcat --pid=$(adb shell pidof com.asmr.player)` → 完成标准：目标功能的行为有日志佐证

长构建用后台运行 + 日志文件跟踪；构建失败时先读 daemon 日志定位（现象与根因的对应关系见踩坑记录），再重试。

## 4. 文件分级约定

写文件前先判断归属：

- **入库**：源码、构建脚本、`docs/`（含本目录）— 必须可移植，不含本机路径
- **本机**：`.gitignore` 覆盖的路径（以 [.gitignore](../.gitignore) 为准，含仓库根 `AGENTS.md`）— 本机专属配置、缓存、密钥、私有指令放这里

新建文件若两类都不属于（如临时脚本、分析产物），先归入本机路径并记录到 devnote，避免污染仓库。

## 5. Agent 运行环境注意事项

以下针对 Trae 沙箱环境下的 Windows 开发：

- **项目目录外的写入可能被沙箱拦截**：换已批准的同级路径重试一次；仍拦截则请用户添加沙箱规则，勿反复尝试
- **PowerShell 写配置文件用无 BOM 方式**：`Set-Content` 默认带 UTF-8 BOM，会静默破坏 Java Properties 首个键（历史坑：JDK 配置失效、构建报裸版本号）。用 Write 工具或 `[IO.File]::WriteAllText` + `UTF8Encoding($false)`
- **`cmd /c` 被禁用**：用 PowerShell 原生语法替代（如管道应答用 `$items | & command`）
- **Java Properties 文件写入后校验编码**：`Format-Hex` 查看前 3 字节是否为 `EF BB BF`

## 6. 重构工作约定

### 6.1 核心原则：行为保持

重构只改结构，不改可观察行为。可观察行为包括：播放与音频链表现、UI 呈现与交互、下载与缓存、数据持久化、通知与前台服务。

- 行为保持是每个子步骤完成标准的一部分：构建成功 ≠ 验证通过，还须行为无差异
- 出现行为差异立即停下：回退该步，或定位根因；只有确认差异是任务文档记录的预期改动才继续
- 纯删除类任务的行为标准更简单：删除对象在调用点清单之外零引用，应用行为即不变

### 6.2 任务循环

1. **领任务** — 从任务列表/计划文档取一个未完成任务，按计划顺序执行 → 完成标准：明确问题编号与涉及文件
2. **取证** — 重读依据文档中该问题的证据部分，打开文件核对现状；报告行号可能因前期任务漂移，以符号搜索为准 → 完成标准：能说出现状与目标的差异点
3. **安全网** — 高风险拆分（巨石文件、播放链、DB）先为待改动行为补测试，确认测试改动前通过、改动后依旧通过；纯删除类改用调用点清单作安全网（grep 全仓库引用，留档进提交说明）→ 完成标准：安全网就位
4. **小步执行** — 一次只做一个可编译子步骤；删除与重命名分开成步，不混排；移动代码保持纯移动（格式化、改名、逻辑调整不与搬运混提交）→ 完成标准：`assembleDebug` 编译通过
5. **验证** — 按 §3 循环执行，行为保持另加目标功能的实机操作对照 → 完成标准：验证循环全部达成，且行为无差异
6. **提交** — 一个任务一个提交（大任务按子步骤拆多个），提交信息以问题编号开头（如 `refactor: P0-1 ...`）→ 完成标准：commit log 可按编号追溯

### 6.3 范围纪律

- 只动任务清单内的代码；顺手发现的相邻问题记入当日 [devnote](archive/refactor-2026/devnote/README.md) 笔记（或 issue 追评），留给后续任务，不当场修
- 新证据处理：发现依据文档未记录的结构问题（新死代码、新重复、新分层穿透）→ 记入当日 devnote；结构性问题补到任务清单并按序编号（如 P1-9），供后续领取

## 7. 阶段门禁（三件套）

重构按阶段推进时，每个阶段收尾必须过三件套，全过才打 tag：

1. **全量测试双绿** — 本机全量测试通过（基线只增不减）+ CI 双绿
2. **子代理审查** — 输入为 `git diff <上阶段tag>..HEAD` + seam 清单 + TDD 反模式清单；发现项按 P0（必须修）/P1（应修）/P2（备忘）分级，首审不通过即诚实记录再闭环
3. **实机走查** — 按本阶段改动面列走查清单，逐项实机验证并留证据（时间轴/日志/截图）

通过后：报告落 `docs/iteration/<阶段>-review.md`，打 tag `refactor-r2/phase-N`（附注）。

## 8. 行为档案机制

重构中"只活在代码里"的隐性行为（回退链、事务顺序、不对称清理）**随改随文档化**：

- 位置：`docs/behavior-notes/`（入库），一 seam 一文件，索引进 ARCHITECTURE.md
- 条目格式：行为描述 / 代码位置 / 触发条件 / 钉测试引用 / 发现于（任务号）
- 触发时机：读代码取证时发现即记，不等重写完成
- **已录行为勿"顺手"清理**：行为档案记录的不对称（如 deleteAlbum 路径不清孤儿表）是原状保留决策，审查时勿报、重构时勿动

## 9. 架构守护修改流程

动 import 禁令或行数 ratchet 时：

- 守护实现：`tools/ci_guard.py`（按文件真实 `package` 行匹配 + 全仓扫描）+ 存量 `tools/import-direction-baseline.txt` + size baseline「路径: 行数上限」格式
- **改规则必须带反例夹具**：每条规则在 `tools/guard-selftest/` 至少一个反例样本，改完跑自检脚本，防规则空转
- 收缩 baseline = 实际还债；新增违规存量入 baseline 并记录偿还计划
