# 重构协作约定

> 本文约定重构分支（`refactor/architecture-cleanup`）上的工作方式。
> 通用仓库约定见 [agent-collab.md](agent-collab.md)（入库可移植性、构建验证循环、文件分级、沙箱注意事项）— 执行任何重构任务前先读它。
> 工作依据：[质量体检报告](../project-quality-review-20260929.md)与重构 issue 的任务列表。问题编号（P0-x / P1-x / P2-x）在报告、issue、commit 三处沿用同一套。

## 核心原则：行为保持

重构只改结构，不改可观察行为。本应用的可观察行为包括：播放与音频链表现、UI 呈现与交互、下载与缓存、数据持久化、通知与前台服务。

- 行为保持是每个子步骤完成标准的一部分：构建成功 ≠ 验证通过，还须行为无差异
- 出现行为差异立即停下：回退该步，或定位根因；只有确认差异是任务文档记录的预期改动才继续
- 纯删除类任务的行为标准更简单：删除对象在调用点清单之外零引用，应用行为即不变

## 任务循环

1. **领任务** — 从 issue 任务列表取一个未完成任务；issue 建立前以报告 §4 分级问题清单、§6 Quick wins、§7 路线图为准，顺序参照 §7（先腐蚀最小化，再专项修补）。→ 完成标准：明确问题编号与涉及文件
2. **取证** — 重读报告中该问题的证据部分，打开文件核对现状；报告行号可能因前期任务漂移，以符号搜索为准。→ 完成标准：能说出现状与目标的差异点
3. **安全网** — 高风险拆分（巨石文件、播放链、DB）先为待改动行为补测试，并确认测试在改动前通过、改动后依旧通过。纯删除类任务改用调用点清单作安全网（grep 全仓库引用，留档进提交说明）。→ 完成标准：安全网就位
4. **小步执行** — 一次只做任务内一个可编译子步骤；删除与重命名分开成步（先删死代码，再摘版本号重命名），不混排。→ 完成标准：`assembleDebug` 编译通过
5. **验证** — 按 [agent-collab.md](agent-collab.md) 构建验证循环执行安装、启动、日志；行为保持另加目标功能的实机操作对照（如拆了专辑详情 → 实际浏览专辑、进入目录面板）。→ 完成标准：验证循环全部完成标准达成，且行为无差异
6. **提交** — 一个任务一个提交（大任务按子步骤拆多个提交），提交信息以问题编号开头，如 `refactor: P0-1 删除目录面板 V1-V4 死代码`。→ 完成标准：从 commit log 可按编号追溯到本次重构的全部改动

## 范围纪律

- 只动任务清单内的代码；顺手发现的相邻问题记入当日 [devnote](README.md) 笔记（或 issue 追评），留给后续任务，不当场修
- 新功能一律新建文件，禁止向 `AlbumDetailScreen` / `MainContainer` 等巨石文件追加（报告 P0-2 约定，重构全程有效）
- 移动代码时保持移动是纯移动：格式化、改名、逻辑调整不与搬运混在同一提交

## 新证据处理

重构中发现报告未记录的结构问题（新死代码、新重复、新分层穿透）：记入当日 devnote 笔记；属结构性问题的补到 issue 追评并按序编号（如 P1-9），供任务循环领取。
